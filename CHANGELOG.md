# Changelog

All notable changes are documented here. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning: [SemVer](https://semver.org/).

## [Unreleased]

### Changed
- The product is now called **Willay** (Quechua for "to warn, to inform"): dashboard, alert emails and sender, Telegram messages, confirmation page and Keycloak realm. The code follows: repository, `willay` package, database and roles, `WILLAY_*` variables, notification channels and Docker images; story IDs keep the `VIG-` prefix. Existing local environments need `docker compose down -v` and the `.env` keys renamed.
- Code, comments and documentation are in English; the product speaks Spanish and English since VIG-40.
- The light theme's subtlest text is a little darker, to reach 4.5:1 on the page background (VIG-41).

### Added
- Monorepo with a Python backend (`willay`), an Angular 22 dashboard, a Makefile and CI on GitHub Actions (VIG-01).
- Docker Compose stack: Postgres (TimescaleDB + PostGIS), Keycloak 26.7 with the `willay` realm and 2 organizations, Mailpit, a `migrate` container, API, 5 workers and dashboard, with healthchecks (VIG-02).
- Initial migrations: `core` and `ingest` schemas, 20 tables, readings hypertable with compression and retention, `willay_owner` and `willay_app` roles with append-only tables (VIG-03).
- `make seed`: Rímac demo data and an isolation organization, with Argon2id station API keys (VIG-04).
- ADR-0001 to ADR-0006 (VIG-05).
- OIDC login in the dashboard with Keycloak and `GET /v1/me`; tokens with zero or several organizations get 403 (VIG-06).
- Per-role permission matrix enforced per endpoint (VIG-07).
- `POST /v1/readings`: batches of up to 500 readings authenticated with the station's API key, limited to 60 batches per minute (VIG-08).
- Late readings (> 1 h) stored without being evaluated, and immediate notification to the evaluator (VIG-09).
- Heartbeat of each station with its latest value and measurement time (VIG-10).
- `make simulate` station simulator with the Rímac demo scenario (VIG-11).
- Versioned OpenAPI contract in `docs/openapi.json`.
- Risk zones: CRUD with geometry validation and auditing, and polygon drawing and editing on the dashboard map (VIG-12).
- Stations: CRUD with their position in each zone, API key rotation shown only once and a dashboard page (VIG-13).
- Evaluator worker: takes readings from the queue with `SKIP LOCKED`, wakes up with `LISTEN/NOTIFY` and marks a reading as failed after 5 attempts (VIG-14).
- Threshold rules and incidents without duplicates, with a copy of the readings that triggered them (VIG-15).
- Rate-of-change rules, measured from peak to trough within the window (VIG-16).
- `silence` worker: one incident per station that stops reporting, recording of its recovery and rate limit purge (VIG-17).
- Cooldown after resolving an incident, and readings that worsen it in its timeline (VIG-18).
- Incidents API: list, detail with timeline, acknowledge and resolve (VIG-19).
- Email alerts when an incident opens, with retries, local time and a confirmation link; visible in Mailpit (VIG-20).
- Telegram linking: a single-use link (7 days) generated by an admin, and a `telegram` worker that stores the contact's chat (VIG-21).
- Telegram alerts with a confirmation button that only works for whoever received the alert; after the click, the button is replaced by who confirmed and when (VIG-22).
- Alert confirmation page without login: opening the link only shows the incident, and the button confirms. Pending alerts of an incident that is already acknowledged or resolved are not sent (VIG-23).
- Automatic escalation by levels with the `escalation` worker, and an escalation policies API for admin (VIG-24).
- Visual system: a single catalog of states (color, icon and text) with contrast tests, navigation by permission, shared loading/empty/error states and formats, and axe-core in every view's tests (VIG-33).
- Live dashboard over SSE (`GET /v1/events`, filtered by organization, the JWT in the header via `eventsource`), with an "En vivo" indicator and 15 s reloads while offline; "Mapa en vivo" with zones by their most urgent incident and stations by state with an incident badge; new incidents announced on every page (VIG-25).
- Incident inbox with status and severity filters kept in the URL; `GET /v1/incidents` filters by severity (VIG-34).
- Incident detail: timeline with who acted, alerts by recipient (`GET /v1/incidents/{id}/alerts`; the email only for operator and admin) and a readings chart (`GET /v1/incidents/{id}/readings`, with the opening evidence once readings expire) (VIG-26).
- Acknowledge, resolve and comment from the incident detail; `POST /v1/incidents/{id}/comments` (VIG-35).
- `make` works from PowerShell and Git Bash on Windows, without WSL.
- Contacts and groups from the dashboard: admin creates, edits and deletes them, generates or unlinks a contact's Telegram link (shown once) and removes a contact with history from its groups; operator reads them. Deleting a group that a policy notifies returns 409 naming the policy (VIG-36).
- Failed readings: `GET /v1/failed-readings` and reprocessing for operator and admin, a live notice on every page while there is any, and the runbook moved to the dashboard (VIG-39).
- Rules from the dashboard: `/v1/rules` with params validated per type, forms per rule type, and `POST /v1/rules/preview` to see where a draft would have opened incidents over the last 24 h. Threshold and rate-of-change rules name their station; only silence rules cover a whole zone (VIG-27).
- Audit log for admin: `GET /v1/audit`, cursor-paginated, and a page with filters by type, author and dates in the URL that shows each changed field in words (VIG-38).
- One `correlation_id` per batch of readings. JSON logs carry it from the reading to its incident and alerts. `received_to_alert_seconds` on each incident's first alert, and `make latency` for p50 and p95 (VIG-28).
- `make loadtest`: 50 stations sending a reading every 10 s for 30 minutes. It checks that no reading is left unevaluated after 120 s and that p95 stays under 30 s (VIG-29).
- `make demo`: the Rímac scenario, narrated in the terminal and judged against SPEC. Level 2 acknowledges by Telegram or, without a bot, from the email. Each run starts from a clean demo organization (VIG-30).
- Spanish and English (VIG-40):
  - the dashboard speaks each user's language, saved for them;
  - API errors carry a stable `code` and a message in the request's `Accept-Language`;
  - timeline reasons appear in each reader's language;
  - emails, Telegram and the confirmation page use each contact's language (new `contacts.language`, defaulting to the organization's).
- Light and dark mode: the dashboard follows the system unless the user picks one in that browser, and the confirmation page follows the device (VIG-41).

### Security
- Map tooltips no longer treat zone and station names as HTML, so a name with markup cannot run in the browser of whoever hovers over it.

### Fixed
- The evaluator and dispatcher workers listen again after a database restart, instead of waking only by their 5 s polling until restarted.
- Two escalation workers no longer escalate the same incident twice when one of them escalated it just before the other locked it.
